# EDU톡 되돌리기 계획

이 문서는 실제 배포 환경을 연결한 뒤 사용할 운영 절차다. 현재 배포 플랫폼, health 경로, 모니터링, 외부 서비스 연결은 확정·운영 중인 상태가 아니다. 실제 플랫폼 이름이나 연락처는 운영 기록에만 추가한다.

## 되돌리기를 시작할 때

- [ ] 중단 기준에 해당하는지 확인하고, 출시 확대를 즉시 멈춘다.
- [ ] 중단 결정 담당자와 현재 단계(staging, 팀, 5%, 25%, 50%, 100%)를 기록한다.
- [ ] 사용자에게는 확인된 영향과 다음 안내 시점만 알린다. 후기 원문, 파일명, 위치, 계정·학생 식별자, 증빙 원본을 적지 않는다.
- [ ] 먼저 feature flag로 문제가 된 기능을 제한할 수 있는지 판단한다.

## 우선순위

1. 개인정보·학생 기록·비공개 증빙 위험이면 해당 기능과 공개 노출을 즉시 중지한다.
2. 결제 상태가 불확실하면 Checkout·Portal 진입과 유료 권한 확대를 중지한다. Stripe 서명 웹훅으로 다시 확인되기 전에는 무제한 권한을 주지 않는다.
3. Supabase·Storage·OpenAI·공공 API 장애면 저장 성공처럼 보이지 않도록 안내하고, 필요한 기능만 feature flag로 끈다.
4. 공개 후기·순위·기관 데이터가 잘못되면 해당 공개 기능을 제한하고 canonical 데이터·승인 상태를 확인한다.

## 이전 배포 복구

- [ ] 현재 배포를 삭제하거나 DB를 바로 되돌리지 않는다.
- [ ] 이전에 정상으로 확인된 배포 버전을 선택해 애플리케이션만 먼저 되돌린다.
- [ ] health/deep health와 로그인·권한·핵심 화면을 확인한다.
- [ ] 문제 기능이 여전히 필요하면 feature flag를 끈 상태로 유지한다.
- [ ] 복구 후 오류·지연·지원 요청이 안정될 때까지 출시 확대를 재개하지 않는다.

## DB와 데이터 원칙

- [ ] DB 변경은 이전 앱 버전도 읽을 수 있는 전방호환 방식으로 먼저 적용한다. 열·테이블 추가, 새 상태값 추가처럼 이전 버전을 깨지 않는 변경을 우선한다.
- [ ] 앱을 먼저 되돌려도 새 DB 구조가 남아 동작해야 한다.
- [ ] 열 삭제, 타입 변경, 필수값 강제, 데이터 삭제처럼 되돌리기 어려운 변경은 별도 승인과 복원 리허설 전에는 production에 적용하지 않는다.
- [ ] 데이터 복원이 필요하면 [백업·복원 체크리스트](./backup-recovery.md)의 staging 리허설 절차를 먼저 따른다. 현재 실제 백업이 설정됐다고 가정하지 않는다.

## 복구 완료 기준

- [ ] health/deep health가 정상이다.
- [ ] 로그인, 권한, 공개 기관·랭킹, 인증·후기, 메시지, AI 사용량, 운영자 요청 흐름이 안정적이다.
- [ ] demo 데이터가 production 화면에 섞이지 않는다.
- [ ] 비공개 증빙과 개인 데이터의 접근 경계가 정상이다.
- [ ] 사용자 안내와 내부 기록에 민감 원문·파일명·위치·식별자를 남기지 않았다.

문제가 해결됐더라도 바로 다음 확대 단계로 가지 않는다. 원인, 영향, feature flag 상태, 재개 조건을 짧게 정리하고 승인받은 뒤 단계적 출시 체크리스트로 돌아간다.
