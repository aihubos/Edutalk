# EDU톡 백업·복원 체크리스트

현재 실제 Supabase 프로젝트, Storage, 백업 일정, 모니터링은 설정된 상태가 아니다. 아래는 제공자 프로젝트 연결 후 운영자가 설정하고 반복할 절차다.

## 백업 설정 전 확인

- [ ] production과 staging 프로젝트를 분리한다.
- [ ] DB 백업 보존 기간, Storage 증빙 보존 기간, 탈퇴·법적 보존 정책을 승인 문서로 확정한다.
- [ ] 백업 접근 권한은 최소 담당자로 제한하고, 운영자 개인 기기에 원본 증빙을 저장하지 않는다.
- [ ] 백업 파일명·운영 로그에 후기 원문, 증빙 파일명, 위치, 계정·학생 식별자를 넣지 않는다.

## 권장 일정

- [ ] DB: 제공자가 지원하는 일일 자동 백업과 시점 복구 설정을 확인한다.
- [ ] 비공개 Storage: 일일 복제 또는 제공자 백업 기능을 설정하고, 객체 경로·메타데이터 복구가 함께 되는지 확인한다.
- [ ] 설정값: 환경변수 값 자체는 백업 문서에 기록하지 않고, 접근 가능한 비밀 관리 도구의 소유자·교체 절차만 기록한다.
- [ ] 주 1회: 백업 성공 여부와 최근 복구 지점을 확인한다.
- [ ] 월 1회: staging에서 복원 리허설을 한다.

## 복원 리허설

1. [ ] 실제 장애가 아닌 staging에서만 시작한다.
2. [ ] 복원 목표 시점과 담당자, 영향 범위를 기록한다. 원문·파일명·개인 식별자는 기록하지 않는다.
3. [ ] DB를 별도 staging 복구 환경에 복원한다.
4. [ ] 필요한 경우 Storage 객체와 메타데이터를 같은 시점으로 복원한다.
5. [ ] 로그인, 공개 canonical 기관 조회, 계정별 권한, 비공개 증빙 접근 차단, 알림·탈퇴 요청 상태를 확인한다.
6. [ ] Stripe 웹훅을 재전송하거나 중복 처리하지 않는다. 결제 상태는 Stripe의 검증된 이벤트와 DB 상태를 비교해 별도 확인한다.
7. [ ] 결과를 성공·실패와 개선 항목만으로 기록한다. 민감 데이터 샘플을 첨부하지 않는다.

## 실제 장애 시

- [ ] 먼저 기능을 제한하거나 feature flag로 중지하고, 사용자가 데이터가 저장됐다고 오인하지 않게 안내한다.
- [ ] 복원 전 현재 상태를 덮어쓰지 말고, 복구 책임자와 목표 시점을 승인한다.
- [ ] Supabase DB, Storage, Stripe, OpenAI, 공공 데이터 중 영향을 받은 범위를 구분한다.
- [ ] 복원 후 공개 랭킹·후기·기관 정보가 demo 데이터와 섞이지 않는지, 권한 없는 증빙 접근이 없는지 확인한다.
- [ ] 사용자 공지는 확인된 영향과 다음 안내 시점만 말한다. 원인 추정이나 타인의 정보는 포함하지 않는다.

## 복원 완료 기준

- [ ] 데이터가 복원됐다는 말보다, 핵심 계정·권한·공개 데이터·비공개 Storage 경계가 정상인지 확인한다.
- [ ] 결제는 Stripe 서명 웹훅과 `ACTIVE` 상태를 다시 확인하기 전까지 무제한 권한을 부여하지 않는다.
- [ ] 리허설 또는 장애 처리 결과와 다음 개선 책임자를 남긴다.

백업·모니터링·복원 리허설이 실제로 설정·기록되기 전에는 이 문서만으로 복구 체계가 운영 중이라고 안내하지 않는다.
